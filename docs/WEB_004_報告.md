## SQL 人工檢查

已人工檢查 SQL 結構，未在 PostgreSQL/Supabase 執行，不能宣稱資料庫驗收通過。這是新專案的一次性 migration，不支援對既有同名資料表直接重跑。

- SELECT：authenticated 可以讀所有人的 `id,nickname,appearance`；時間戳不授權讀取。
- INSERT：只授權寫 nickname、appearance；id 預設 auth.uid()，RLS 再確認 id 等於當前帳號。玩家不能指定別人的 id 或時間戳。
- UPDATE：USING 與 WITH CHECK 都限制自己的 id，欄位權限僅開 nickname、appearance；updated_at 由觸發器更新。
- DELETE：無授權、無 policy，玩家不能刪資料。auth.users 刪除時由外鍵 cascade 清除。
- anon 與 PUBLIC：撤銷資料表所有權限。新帳號觸發器使用 security definer 與固定空 search_path，全限定資料表名稱，函式不對用戶開放呼叫。
- SQL Editor 預設身分能繞過 RLS，所以附錄測試會切換到 authenticated 並設定測試帳號 sub。修改他人的資料預期 UPDATE 0；修改受保護欄位預期權限錯誤。

參考官方文件：[PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow)、[OAuth](https://supabase.com/docs/reference/javascript/auth-signinwithoauth)、[欄位權限](https://supabase.com/docs/guides/database/postgres/column-level-security)、[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)。

## 使用者設定步驟（接線完成後才啟用）

1. 在 Supabase 建立專案，開 SQL Editor，貼上 `server/supabase/001_profiles.sql` 執行一次。
2. 到 Google Cloud Console 建立專案，設定 OAuth 同意畫面；測試模式加入要測試的 Google 帳號。
3. 建立 OAuth 用戶端，類型選網頁應用程式。授權的重新導向 URI 填 Supabase Google Provider 顯示的 `https://xxxx.supabase.co/auth/v1/callback`。
4. Supabase → Authentication → Providers → Google：啟用，填 Google Client ID 與 Secret，儲存。Secret 只填在管理介面，不放進遊戲檔案。
5. Authentication → URL Configuration：Site URL 設 `https://volleycourts.vercel.app`。Redirect URLs 加入該網址及 `http://localhost:5190`；若實際從 `/index.html` 開啟，也加入對應完整路徑。OAuth redirectTo 使用當前頁面，允許清單要吻合。
6. 取得專案 URL 與 anon public key，填入 `auth-config.js` 的兩個值。**本輪尚未接線，現在填值不會顯示登入畫面。**
7. 下一輪完成接線後，本機以 5190 埠開啟網站，依序測 Google 登入、取暱稱、捏臉、重新整理、改外觀、撞名、登出及第二帳號；執行 SQL 檔尾端兩帳號驗證。
